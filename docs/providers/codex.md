# Codex provider

The daemon-side adapter resolves a canonical native `codex` executable from an explicit absolute override, `PATH`, official npm or standalone layouts, or supported desktop-app locations. Candidate searches are bounded and validate the platform's native file signature before and after canonicalization. Package-manager `.cmd`, PowerShell, JavaScript, and shell shims are never parsed or executed. The adapter then runs bounded `codex --version` and `codex login status` probes and launches the interactive CLI using an executable plus argument vector. Optional prompt, model, effort, working directory, profile, and resume ID are separate arguments; no user text is interpolated into a shell command. An initial prompt remains transient: the provider process receives it, but the persisted launch record excludes it and no prompt history row is written.

The environment starts from a platform allowlist, retains `CODEX_HOME` so an existing login remains usable, injects only SylvOps session/worktree/hook identifiers, and excludes GitHub and provider API-key variables. SylvOps never initiates login, copies credentials, persists auth state, or logs environment values.

SylvOps atomically installs a stable `$CODEX_HOME/sylvops-hooks-v1-<content-hash>.config.toml` layer and launches Codex with `--profile <name>`. Its identity includes the validated relay path and hook definitions, never a Session ID, endpoint, or credential. Concurrent Sessions reuse the same verified hook definitions. Changed definitions or installations get a new source rather than overwriting a profile used by a running Session. Session deletion and daemon restart preserve the shared profile, user preferences, and trust metadata; startup never sweeps profiles that another daemon could still use. Profiles with altered protected hooks or unsafe file identity are refused rather than overwritten. The base user configuration and repository files are untouched.

Codex requires explicit review/trust of non-managed hooks. Review the SylvOps source with `/hooks` when prompted; stable unchanged sources are intended to reuse that approval. SylvOps never alters Codex trust records or passes `--dangerously-bypass-hook-trust`. Changed relay paths/definitions can legitimately require approval again. Trust reuse must be verified against the real supported Codex version; fake-provider tests cannot prove Codex's trust UI behavior.

In the `/hooks` browser, review the generated SylvOps source, press `t` to trust its hooks, and verify that they are Active. Then submit a prompt. Desktop and TUI show Conversation identity readiness separately from callback health: a working terminal or a received callback alone does not guarantee that resume is ready. A terminal Session whose identity was never recorded cannot be backfilled; its history remains available and Start Fresh creates a new Conversation.

Codex may write model, permissions, `[tui]` status-line/theme/keybinding preferences, and future provider settings into the selected profile. SylvOps preserves the entire file byte-for-byte and validates only its protected configuration: `features.hooks` must remain `true`, and the complete hook definitions, ordering, commands (including Windows commands), execution options, and timeouts must match the generated definition. Other settings are owned and validated by Codex, including its permission requirements; SylvOps does not maintain a preference-key allowlist. Unsupported or invalid provider settings can still produce Codex configuration errors.

Codex may append `[hooks.state]` approval hashes and Project trust metadata to the stable profile. SylvOps preserves those records verbatim and accepts only bounded approval entries for the same profile's generated hooks and valid Project trust records. Unknown hook events/types or additional handlers are rejected. `SessionEnd` remains synchronous, as required by Codex. The whole profile remains limited to 64 KiB and must be valid UTF-8 TOML with the expected ownership marker and a revalidated regular-file identity. Cleanup uses separate, stricter ownership checks and never removes shared profiles or treats preference acceptance as permission to delete user settings.

Upgrading from Preview 13 recovers profiles rejected solely because Codex saved status-line or other provider preferences: no profile deletion, renaming, or manual migration is required. The existing source path and hook definitions are reused, preserving saved approvals. This does not repair malformed configuration, changed protected hooks, or unsafe file identities; those failures receive distinct bounded diagnostics without printing configuration values.

The relay reads one bounded JSON object, sends it to the authenticated loopback receiver, emits no approving/denying output, and applies strict time and body limits. Session credentials and endpoint remain per-process environment values. Callback health is separate from process health: after 15 seconds without an accepted callback, clients show missing-monitoring guidance. Approving hooks after startup and submitting another prompt can recover monitoring without restarting the Session. No terminal-text or inactivity heuristic creates completion/input attention. PermissionRequest is supported; ordinary user-question elicitation currently has no mapped Codex callback.

The receiver captures documented session IDs for guarded `codex resume <id> --cd <verified-worktree>`. Unknown, duplicate, stale, identity-mismatched, or malformed events cannot silently change state; relevant refusals are audited without persisting raw payloads.

On Windows, the hook command serializes the validated relay executable as an ordinary drive or UNC path rather than a verbatim (`\\?\`) path. The daemon revalidates that this spelling resolves to the same canonical executable and refuses control characters, quotes, and environment-expansion characters (`%` and `!`). The relay arguments are always `hook emit`; model, prompt, repository, and Provider data cannot extend them. The default generated-command integration test runs fake Codex through the Windows `cmd.exe /C` contract (or the Unix shell contract), including an installation path with spaces and non-ASCII characters, then verifies Conversation identity through daemon IPC and after restart.

Real-account tests are opt-in. Default tests use the fake agent.

## Interactive acceptance

Use a scratch Project and the real installed Codex; approve SylvOps hooks normally. With one client connected before the event, submit a short prompt, select another Session or background the client, and verify completion attention plus notification. Change status-line settings with `/statusline`, then repeat in a second Session, after daemon restart, and after Resume Conversation. Verify that preferences persist, the same profile path is reused, unchanged hooks do not request renewed approval, callback health is ready, and input/completion attention plus background notifications still arrive. Also test approving after startup, then submitting a prompt; callback health should recover within five seconds of an accepted callback. Never bypass hook trust for this check.

In both clients, Settings → Test notification exercises saved visual/sound preferences without a provider or Attention Event. OS policy may suppress visible display. Windows native adapter smoke coverage is explicit: `cargo test -p sylvops-desktop notifications::tests::windows_native_notification_smoke_is_bounded -- --ignored --exact`. Run it only in an interactive desktop session. Adapter acceptance is not a visual-display assertion. The TUI Active cards/list retain reason-specific colors until explicit review/resolution; desktop navigator and tabs have no attention background tint. Use Mark reviewed or Ctrl+Shift+R in the TUI to review an already-open completion/failure.

An ignored real-account test is available with `SYLVOPS_REAL_CODEX_PATH` set to an absolute native Codex executable: `cargo test -p sylvops-test-support --test codex_hook_command real_codex_delivers_completion_across_sessions_and_daemon_restart -- --ignored --exact`. It uses a scratch Project, fixed prompts, and a 180-second bound; it requires existing login and prior explicit approval of the stable `hook-daemon` source. That source differs from the installed application's relay. No test bypasses hook trust or prints environment values or PTY output. Default tests require neither a real provider nor account access.

Interface assumptions are limited to the documented [Codex CLI commands](https://developers.openai.com/codex/cli/reference), [authentication behavior](https://developers.openai.com/codex/auth), and [hook contract](https://learn.chatgpt.com/docs/hooks).
