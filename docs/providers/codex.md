# Codex provider

The daemon-side adapter resolves a canonical native `codex` executable from an explicit absolute override, `PATH`, official npm or standalone layouts, or supported desktop-app locations. Candidate searches are bounded and validate the platform's native file signature before and after canonicalization. Package-manager `.cmd`, PowerShell, JavaScript, and shell shims are never parsed or executed. The adapter then runs bounded `codex --version` and `codex login status` probes and launches the interactive CLI using an executable plus argument vector. Optional prompt, model, effort, working directory, profile, and resume ID are separate arguments; no user text is interpolated into a shell command. An initial prompt remains transient: the provider process receives it, but the persisted launch record excludes it and no prompt history row is written.

The environment starts from a platform allowlist, retains `CODEX_HOME` so an existing login remains usable, injects only SylvOps session/worktree/hook identifiers, and excludes GitHub and provider API-key variables. SylvOps never initiates login, copies credentials, persists auth state, or logs environment values.

SylvOps atomically installs a stable `$CODEX_HOME/sylvops-hooks-v1-<content-hash>.config.toml` layer and launches Codex with `--profile <name>`. Its identity includes the validated relay path and hook definitions, never a Session ID, endpoint, or credential. Concurrent Sessions reuse the same verified hook definitions. Changed definitions or installations get a new source rather than overwriting a profile used by a running Session. Session deletion and daemon restart preserve the shared profile, user preferences, and trust metadata; startup never sweeps profiles that another daemon could still use. Profiles with altered protected hooks or unsafe file identity are refused rather than overwritten. The base user configuration and repository files are untouched.

Codex requires explicit review/trust of non-managed hooks. Review the SylvOps source with `/hooks` when prompted; stable unchanged sources are intended to reuse that approval. SylvOps never alters Codex trust records or passes `--dangerously-bypass-hook-trust`. Changed relay paths/definitions can legitimately require approval again. Trust reuse must be verified against the real supported Codex version; fake-provider tests cannot prove Codex's trust UI behavior.

In the `/hooks` browser, review the generated SylvOps source, press `t` to trust its hooks, and verify that they are Active. Then submit a prompt. Desktop and TUI show Conversation identity readiness separately from callback health: a working terminal or a received callback alone does not guarantee that resume is ready. A terminal Session whose identity was never recorded cannot be backfilled; its history remains available and Start Fresh creates a new Conversation.

Codex may write model, permissions, `[tui]` status-line/theme/keybinding preferences, and future provider settings into the selected profile. SylvOps preserves the entire file byte-for-byte and validates only its protected configuration: `features.hooks` must remain `true`, and the complete hook definitions, ordering, commands (including Windows commands), execution options, and timeouts must match the generated definition. Other settings are owned and validated by Codex, including its permission requirements; SylvOps does not maintain a preference-key allowlist. Unsupported or invalid provider settings can still produce Codex configuration errors.

Codex may append `[hooks.state]` approval hashes and Project trust metadata to the stable profile. SylvOps preserves those records verbatim and accepts only bounded approval entries for the same profile's generated hooks and valid Project trust records. Unknown hook events/types or additional handlers are rejected. `SessionEnd` remains synchronous, as required by Codex. The whole profile remains limited to 64 KiB and must be valid UTF-8 TOML with the expected ownership marker and a revalidated regular-file identity. Cleanup uses separate, stricter ownership checks and never removes shared profiles or treats preference acceptance as permission to delete user settings.

Upgrading from Preview 13 recovers profiles rejected solely because Codex saved status-line or other provider preferences: no profile deletion, renaming, or manual migration is required. The existing source path and hook definitions are reused, preserving saved approvals. This does not repair malformed configuration, changed protected hooks, or unsafe file identities; those failures receive distinct bounded diagnostics without printing configuration values.

Managed Sessions require a native CLI advertising `--remote`, `--remote-auth-token-env`, and stdio app-server support. SylvOps owns a private backend process tree and connects the native terminal through a one-connection authenticated IPv4-loopback bridge. The backend uses private stdio; bridge messages are capped at 1 MiB, outstanding requests at 128, and event delivery is bounded. The ephemeral bearer token is passed through the child environment, never command-line text or persisted launch arguments. Browser Origin handshakes and unauthenticated connections are refused. Terminal exit, explicit Stop, startup failure, or runtime failure also cleans up the backend.

Actual command, file-change, additional-permission, question, and MCP elicitation requests establish Waiting for input and one pending Attention Event. Responses remain in the native Codex terminal. The bridge never supplies an answer, changes permission decisions, or auto-resolves a question after a timeout. Confirmation through `serverRequest/resolved` clears waiting only when every request has resolved. New distinct requests can restore unread emphasis after review; output, snapshots, and observational hooks cannot clear unanswered input.

Asynchronous question messages carry structured question data but do not themselves block Codex. SylvOps requests a native turn interruption, preserves the question in Conversation history, and retains Waiting for input until the user's explicit reply is accepted as a new turn. That deliberate interruption does not generate a completion notification. Plain explanatory text, including a question mark without structured question data, does not pause work. No terminal-text or inactivity heuristic creates input attention.

The legacy hook relay still accepts one bounded JSON object and emits no approving/denying output. Callback health is independent of process health; accepted structured events also establish monitoring readiness and Conversation identity. Existing hook profiles, user preferences, and trust metadata remain untouched. Running Sessions retain their original runtime until they end; start or Resume a Session to use the bridge.

The receiver captures documented session IDs for guarded `codex resume <id> --cd <verified-worktree>`. Unknown, duplicate, stale, identity-mismatched, or malformed events cannot silently change state; relevant refusals are audited without persisting raw payloads.

On Windows, the hook command serializes the validated relay executable as an ordinary drive or UNC path rather than a verbatim (`\\?\`) path. The daemon revalidates that this spelling resolves to the same canonical executable and refuses control characters, quotes, and environment-expansion characters (`%` and `!`). The relay arguments are always `hook emit`; model, prompt, repository, and Provider data cannot extend them. The default generated-command integration test runs fake Codex through the Windows `cmd.exe /C` contract (or the Unix shell contract), including an installation path with spaces and non-ASCII characters, then verifies Conversation identity through daemon IPC and after restart.

Real-account tests are opt-in. Default tests use the fake agent.

Completion, failure, and input attention can be reviewed by successfully opening the TUI card, or using Mark reviewed / Ctrl+Shift+R while it is already open. Reviewing input removes unread emphasis but leaves Waiting for input; it neither answers nor resumes the Provider. Merely focusing the window or selecting a card does not review it. Codex observational permission checks do not create input attention.

Managed profiles continue to observe PreToolUse, PostToolUse, and PermissionRequest without making decisions. PermissionRequest fires before automatic review as well as interactive approval, so it remains neutral. The private structured transport establishes actual input attention instead. Observational hooks cannot override a structured waiting condition. Claude permission and user-input attention are unaffected.

Completion and failure attention still notify normally. The existing one-second input-notification delay, saved preferences, cross-client coordination, and foreground suppression also apply to actual Codex input requests. Protocol 1.36 requires restarting daemon and clients together. No database migration or hook-trust change is required. Private remote-terminal transport is experimental upstream, so real-provider acceptance is required before preview promotion.

## Interactive acceptance

Run `cargo test -p sylvops-test-support --test codex_input` for offline end-to-end coverage of blocking questions, asynchronous-question interruption and reply, command/file/permission approvals, MCP elicitation, notification claims, review without resolution, and backend-descendant cleanup. This uses fake binaries and requires no account.

Before promoting a preview, explicitly opt into a scratch real-account check: trigger a question with answer controls, an asynchronous question, and a command needing human approval under your existing permission settings. Leave each unanswered beyond one second with the Session in the background: verify orange attention, Waiting for input, a stopped Working indicator, and one notification. Review without answering and verify that waiting persists. Answer or decline in the native terminal and verify continuation; for the asynchronous question, verify that the paused turn does not emit a completion alert. Repeat after detach/reconnect and Resume. Also run an automatically approved command and verify no input alert. Do not bypass hook trust or change permission policy for this check.

Use a scratch Project and the real installed Codex; approve SylvOps hooks normally. With one client connected before the event, submit a short prompt, select another Session or background the client, and verify completion attention plus notification. Change status-line settings with `/statusline`, then repeat in a second Session, after daemon restart, and after Resume Conversation. Verify that preferences persist, the same profile path is reused, unchanged hooks do not request renewed approval, callback health is ready, permission checks stay neutral, and completion attention plus background notifications still arrive. Check that actual approval prompts remain usable in the terminal. Also test approving after startup, then submitting a prompt; callback health should recover within five seconds of an accepted callback. Never bypass hook trust for this check.

In both clients, Settings → Test notification exercises saved visual/sound preferences without a provider or Attention Event. OS policy may suppress visible display. Windows native adapter smoke coverage is explicit: `cargo test -p sylvops-desktop notifications::tests::windows_native_notification_smoke_is_bounded -- --ignored --exact`. Run it only in an interactive desktop session. Adapter acceptance is not a visual-display assertion. The TUI Active cards/list retain reason-specific colors until explicit review/resolution; desktop navigator and tabs have no attention background tint. Use Mark reviewed or Ctrl+Shift+R in the TUI to review an already-open completion/failure event. Codex permission checks require no review.

An ignored real-account test is available with `SYLVOPS_REAL_CODEX_PATH` set to an absolute native Codex executable: `cargo test -p sylvops-test-support --test codex_hook_command real_codex_delivers_completion_across_sessions_and_daemon_restart -- --ignored --exact`. It uses a scratch Project, fixed prompts, and a 180-second bound; it requires existing login and prior explicit approval of the stable `hook-daemon` source. That source differs from the installed application's relay. No test bypasses hook trust or prints environment values or PTY output. Default tests require neither a real provider nor account access.

Interface assumptions follow the documented [Codex app-server protocol](https://learn.chatgpt.com/docs/app-server), [CLI commands](https://developers.openai.com/codex/cli/reference), [authentication behavior](https://developers.openai.com/codex/auth), and [hook contract](https://learn.chatgpt.com/docs/hooks). Codex 0.163.0's generated schemas also define `isBlocking` and typed asynchronous AgentMessage questions; unsupported request types fail closed.
