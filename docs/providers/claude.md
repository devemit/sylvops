# Claude Code provider

Claude Code follows the same adapter boundary as Codex: bounded discovery and health probes, structured launch arguments, a reviewed environment, and managed hook configuration that preserves effective user, project, and organization settings. SylvOps launches the verified native executable in the selected Worktree and never selects a permission mode.

The daemon adds one atomic, application-owned `--settings` layer for its lifetime. The layer contains no credentials and does not edit Claude user or Project files. It uses direct observational HTTP hooks where Claude supports them. Because Claude Code does not run HTTP handlers for `SessionStart`, that event uses the fixed SylvOps hook relay in documented executable-and-argument form; the relay forwards the unchanged bounded payload to the same authenticated loopback receiver. Per-Session credentials and identity headers come only from the child environment and are invalidated on every failure or terminal path.

The layer observes `UserPromptSubmit`, `PermissionRequest`, `SubagentStart`, `SubagentStop`, `Stop`, `StopFailure`, and `SessionEnd`. A narrowly matched `PreToolUse` observer covers only `AskUserQuestion` and `ExitPlanMode`. These handlers return no decision payload, so they never approve, deny, answer, rewrite, or continue Claude activity. `Stop` uses only the presence of bounded `background_tasks` and `session_crons` entries; `StopFailure` records only Claude's documented bounded error category and never its error details or rendered message.

Model and effort values are validated by the Claude adapter and passed as separate arguments. An optional initial prompt is a transient final argument and is excluded from persisted arguments, logs, audit events, and SQLite.

Claude Code is enabled by default while Shell remains the default selection. Configuration version 2 adds Claude Code only when migrating the exact version-1 default provider list; customized provider lists remain unchanged. The CLI, TUI, and desktop create Claude Sessions in a selected Worktree through authenticated IPC. Interactive forms expose only the Provider and optional display name; model, effort, and initial prompt remain CLI-only, and interactive prompting happens in the attached Claude Terminal.

Client availability, authentication validation, recovery guidance, and resume affordances consume the daemon-returned health and capabilities. Missing installation, old version, unsupported authentication, and logged-out diagnostics tell the user what to do outside SylvOps and offer an explicit health refresh; SylvOps never installs, updates, or logs in to Claude Code. Claude cloud Sessions, background-agent management, Remote Control, plugins, and enterprise authentication are not supported or advertised.

A managed Claude Session expects an authenticated `SessionStart` within 15 seconds. If the process is still live without it, the Session becomes needs feedback with bounded recovery guidance while its Terminal remains attached and usable. A later valid lifecycle event clears the warning and applies that event's normal attention transition, but only an authenticated `SessionStart` may establish the verified Claude session ID.

The first verified identity is persisted with the Session. A later identity may replace it only for an authenticated `SessionStart` whose documented source is `clear` or `resume`; the identity update and its redacted audit record commit atomically. Other changes are refused without replacing the last verified ID. Eligible finished, failed, or disconnected Sessions resume through structured `claude --resume <verified-id>` arguments in the same revalidated Worktree. Resume creates one successor SylvOps Session and preserves the source record; concurrent, stale, live-owner, terminated, missing-ID, and Worktree-mismatch attempts fail deterministically. SylvOps never selects Claude's continue-latest, named-session, or fork-session behavior.

No implementation may infer permission or input requests by scraping terminal text. Default tests use the fake agent and require no authenticated account.
